## The portfolio on Netlify

| Setting | Value |
|---|---|
| Base directory | *(repository root)* |
| Build command | `pnpm install --frozen-lockfile && pnpm --filter @gip/portfolio build` |
| Publish directory | `apps/portfolio/dist` |
| Node version | `22` |

**The SPA redirect.** The portfolio is a single-page application, so every
path must serve `index.html` and let the router handle it. The rule lives in
two places: `netlify.toml`, and `apps/portfolio/public/_redirects`, which Vite
copies into the published output.

The second copy is the one that matters. It travels with the build artefact,
so the fallback works regardless of which directory Netlify reads its
configuration from. The first deploy 404'd on every route except the root
because `netlify.toml` had not been committed — the `_redirects` file removes
that class of failure.

## The services on Render

| Setting | Value |
|---|---|
| Root directory | `services/<service-name>` |
| Build command | `pnpm install --frozen-lockfile && pnpm --filter @gip/<service-name> build` |
| Start command | `pnpm --filter @gip/<service-name> start` |
| Instance type | Free |

The root directory is the setting that is easiest to get wrong. With it
empty, the build runs from the repository root and the start command cannot
find the service.

## Environment variables

### The services

Each service's variables are generated by `pnpm db:setup:neon` and written to
`.env.render`, which is **gitignored**. Nothing sensitive is in the
repository.

| Variable | Purpose |
|---|---|
| `NODE_ENV` | `production` |
| `PORT` | `10000` — Render's default, which it forwards to the service |
| `DATABASE_URL` | The Neon **pooled** URL for that service's own role |
| `JWT_SECRET` | The shared signing secret. **Identical on all three services** |
| `JWT_ISSUER` | `gip-auth` |
| `JWT_AUDIENCE` | `gip` |
| `CORS_ORIGINS` | The portfolio's origin, plus `http://localhost:5173` |
| `RUN_MIGRATIONS` | `true` — applies the migrations on startup |

**Each service has its own `DATABASE_URL`**, differing only in the role and
password. The role owns one schema and cannot reach the others, so the
isolation is enforced by PostgreSQL rather than by convention.

**All three services share one `JWT_SECRET`.** The auth service signs tokens
with it and the other two verify with it. If they differ, every authenticated
request fails with 401.

### The portfolio

`VITE_*` variables are **public** — they are bundled into the JavaScript

## The database on Neon

One project, three schemas, each owned by its own restricted role.

| Schema | Role | Service |
|---|---|---|
| `lost_found` | `lost_found_role` | Lost & Found API |
| `auth` | `auth_role` | Authentication API |
| `flash_sale` | `flash_sale_role` | Flash Sale API |
| `<schema>_test` | `<schema>_test_role` | The integration tests |

**The schema is selected by the role's `search_path`, not by a startup
parameter.** Neon's pooler rejects `search_path` in the startup package
("unsupported startup parameter in options: search_path"), so setting it on
the role is what makes the same code work on both the local instance and the
hosted one. The pooler applies role settings at login.

Verified on the hosted instance:

```
lost-found   own schema writable: yes   cannot write to public   cannot read another service's tables
auth         own schema writable: yes   cannot write to public   cannot read another service's tables
flash-sale   own schema writable: yes   cannot write to public   cannot read another service's tables
```

A service role also needs `CONNECT` on the database itself, not only
ownership of a schema inside it.

### Setting up a database

```bash
DATABASE_URL=<the Neon owner URL> pnpm db:setup:neon
```

This creates the roles, the schemas, the grants, and writes the per-service
environment blocks to `.env.render`.

## The free tier, and what it means

**Render sleeps the services.** A free web service spins down after 15
minutes without traffic and takes about a minute to wake. The first request
after a sleep is genuinely slow — the portfolio's API tester shows a
"warming up" state and retries once.

**Neon does not lose data.** It scales to zero after five minutes of
inactivity and resumes in about 200 ms. This is why it was chosen over
Supabase, whose free tier **pauses a project after a week of inactivity** and
needs a manual dashboard click to resume — a jury opening a week-old demo
would see a dead backend.

**Render may suspend a service** that generates "an uncommonly high volume
of traffic over the public internet", with accessing an external database
given as the example. The Flash Sale concurrency lab is therefore capped to a
modest number of simultaneous requests. If the service is ever suspended,
that is the likely reason.

**Rendering's free Postgres expires 30 days after creation**, so it is not
used.

## Recovering

The database is the only stateful part, and it survives a service being
rebuilt or replaced. To redeploy a service, push a commit or press
**"Manual Deploy"** in Render. The migrations are applied on startup and are
recorded, so running them again is a no-op.
